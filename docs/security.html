Security hardening

What protects Paper to Notebook, and why. The app sends untrusted papers to an LLM and can run the code the model writes, on a server that usually runs on your own machine. This page covers the automated checks, cross-site and CORS protection, the run check (agentic code execution), prompt injection, API keys, input validation, resource limits and dependencies, plus the review findings and the risks that remain.

1. How security is checked

Four layers, from automatic on every change to an occasional deep review. Tools catch known patterns; people (or Claude) catch design problems. The wildcard CORS setting, for example, was flagged by a tool, but it only became serious once the run check existed, which only a review could see.

3. Cross-site requests, CORS and DNS rebinding

A server on localhost isn't private. Any web page you visit can make your browser send it requests. A plain form POST needs no permission (no CORS preflight), and it arrives from 127.0.0.1.

What was wrong

  • Wildcard CORS. allow_origins=["*"] with allow_credentials=True echoed any origin back, so every website could read the API from your browser. Found by Semgrep and confirmed with curl.
  • Cross-site POSTs. A page could start a paid conversion and, since the request came from 127.0.0.1, pass the run check's localhost rule.
  • DNS rebinding. A page that points its own domain at 127.0.0.1 becomes "same-origin" with the server, gets past a same-origin check, and can read the responses. Found in the manual review.

What is in place now

  • No CORS at all. The dashboard is served from the same address it calls, so it needs no cross-origin permission. Other sites get no Access-Control-Allow-* headers, so the browser won't let them read responses.
  • Same-origin guard (require_same_origin in api/dependencies.py) on POST /convert and POST /convert/stream. Browsers mark cross-site requests with Sec-Fetch-Site (and Origin in older browsers), and pages can't forge those headers. Cross-site, same-site (another localhost port) and null origins get 403 before any work starts. Requests without those headers, such as curl and scripts, are allowed.
  • Host allow-list (HostCheckMiddleware in api/security.py). Only localhost, 127.0.0.1 and ::1 are served, plus any names in [app] allowed_hosts; everything else gets 400. This defeats DNS rebinding, because the rebound request still carries the attacker's host name. Starlette's built-in middleware wasn't used because it mishandles IPv6 hosts like [::1]:8000.
  • The run check also requires a localhost Host header, as a second line of defence.

Verified against a live server: other origins get no CORS headers; a cross-site POST gets 403; a rebound host gets 400 on both reads and POST /convert with verify=true; the dashboard still works.

5. The run check: executing LLM-written code

"Check that the notebook runs" runs every code cell with QUICK_RUN = True. If a cell fails, it sends the error back to the model for a fix and runs again. That's agentic code execution: code written by a model (and possibly steered by the paper) runs on the server.

Defences

  • Opt-in per run: unticked by default ([verify] default = false). The hint reads "on this computer, with your permissions… only for papers you trust".
  • Localhost only: offered only when the client is 127.0.0.1 or ::1 and the Host header is a localhost name (verify_allowed), unless [verify] allow_remote = true.
  • Separate process: sandbox_runner.py runs in its own Python process with a minimal environment (no API keys), a throwaway working folder, its own virtual environment, per-cell and whole-run timeouts, and the whole process group killed on timeout.
  • Package allow-list: only packages in [verify] allowed_packages (33 common scientific and ML packages) are installed in the sandbox. Others the notebook asks for are skipped and reported, so a paper can't get an arbitrary PyPI package installed on your machine. The downloaded notebook still lists every package for Colab.
  • GPU notebooks skipped, and repairs capped at max_repairs (2).

Limits, stated honestly

The sandbox is not a defence against malicious code. It runs as your user, so it can read your files, use the network, and read the server's API key from the process list (ps eww <pid> on macOS). The clean environment only prevents accidental leaks. Proper isolation needs a container with no network, or a separate OS user. That's required before any remote use. Until then, the localhost-only rule, the package allow-list and the "papers you trust" rule keep the risk acceptable for a local tool.

Two Semgrep findings, exec() and shell=True in sandbox_runner.py, are this intended behaviour. They're annotated with # nosemgrep and a reason.

6. Prompt injection

The uploaded or fetched PDF goes to the configured model (Anthropic, Gemini or OpenAI). Anyone can write a paper, or publish one on arXiv, containing hidden instructions. The app doesn't try to detect injection. Instead, it limits what model output can do:

Model outputWhere it goesHow it's handled
Notebook text, reasoning summary, cell output, errorsDashboardAlways set with textContent, never parsed as HTML; the CSP blocks injected scripts.
pip_packagesThe notebook's !pip install cellFiltered to plain package names (_PACKAGE_SPEC) and shell-quoted, so no other shell commands can run. Others are dropped and shown as "unsafe dropped".
pip_packages during the run checkThe sandboxOnly allowed packages are installed (§5).
Code cellsThe run checkExecuted, which is the main risk; see the limits in §5.
Code cellsThe downloaded notebookEvery notebook begins with "Review the code before relying on its results". You choose what to run in Colab.
Title and filenameSaved file and download headerReduced to plain ASCII by sanitize_filename.
Repair fixesThe notebook specApplied only to existing cell numbers, as strings; anything else is ignored.

The worst case is a chain: a malicious page uses DNS rebinding, starts the run check with a poisoned paper, the injected code runs, and it reads the key. Each link in that chain is now blocked: §3 stops the rebinding, §5 keeps the check local and opt-in, and the package allow-list limits what can be installed.

7. API keys and secrets

  • Keys are read only from environment variables, named by api_key_env in config.toml. Never from files or requests. .env is git-ignored.
  • Keys are logged only through mask_secret, e.g. sk-a…7f2c (33 chars). ProviderSettings.__repr__ and describe_key() mask too.
  • Keys never appear in /api/config (it shows only which variable held the key), error messages, the notebook "recipe", notebook metadata, or the sandbox's environment. Tests check this.
  • A search of all tracked files and the full git history found only two obvious test fakes, and no committed .env or key files.
  • Three Semgrep "credential in log" findings were false positives: a masked key and token counts. They're annotated with the reason.

9. Resource and cost limits

  • Concurrent conversions: at most [app] max_concurrent_conversions (default 2). More get 429 with Retry-After. A slot is taken only after the input is validated, and it's released on success, failure or client disconnect. Verified: 6 at once gives 2 running and 4 refused.
  • Sizes: 15 MB for uploads and arXiv PDFs.
  • Time: arXiv lookup and download timeouts; per-cell and whole-run timeouts in the run check; a capped number of repairs.
  • Binding: run.py listens on 127.0.0.1 by default. Set HOST=0.0.0.0 only on purpose. Ruff's S104 rule flagged the old 0.0.0.0 default.

10. Dependencies and supply chain

  • pip-audit checks every installed package, including indirect ones, against the public vulnerability database on every check and in CI. If a package is vulnerable, the rule is to raise its minimum version in pyproject.toml.
  • CI actions are pinned to full commit SHAs (actions/checkout v4.4.0, astral-sh/setup-uv v6.8.0), with the version in a comment. A tag can be moved to other code by the action's owner; a SHA can't. The workflow explains how to update.
  • uv installs everything. CI resolves versions from pyproject.toml on each run, because uv.lock is git-ignored by choice.
  • Packages the model asks for go through the run check's allow-list (§5). In Colab, you choose whether to run the install cell.

12. Remaining risks

  • The run check isn't isolated (F2). Acceptable for a local, opt-in tool used on papers you trust. Before remote use, run it in a container without network access or home-folder access, or as a separate OS user.
  • No authentication (F6). Anyone who can reach the server can spend your key, list and download notebooks, and see server paths. Keep it on localhost, or put it behind an authenticating proxy and list its host in [app] allowed_hosts.
  • Generated notebooks are untrusted. Review the code, and the packages it installs, before running it in Colab.
  • Dependency versions aren't locked (uv.lock is git-ignored). Each CI run audits the latest versions allowed by pyproject.toml, which is good for catching new CVEs but means builds aren't fully reproducible.
  • Semgrep's rules change over time, so a new rule can occasionally flag existing code and fail CI. Triage it with the skill's rules: fix real issues, and annotate intended behaviour with a reason.

14. Keeping it this way

  1. Run ./check.sh after every change; CI enforces it. Fix findings rather than silencing them. Annotate only intended behaviour or false positives, one line at a time, with a reason. Never use blanket ignores or --no-verify.
  2. For new endpoints, subprocesses, file handling, fetched URLs, key handling or dashboard code, follow the security-hardening skill's checklist. In particular, a new POST endpoint needs require_same_origin, a test that a cross-site request gets 403, and, if it's costly, a conversion slot.
  3. Run /security-review on pending changes before committing larger features.
  4. Do a manual security review (the skill's section 5) before any deploy or release, and update this page with the results.
