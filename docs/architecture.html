How the pieces fit together

A PDF goes in through the dashboard, one LLM call turns it into a notebook spec, and the server builds, saves and streams back a Colab .ipynb. Below: which subsystems exist, who calls whom, and the order of events in one conversion.

3. Worked example

One paper, attention.pdf, followed through the four stages. The LLM writes the content as JSON; ordinary code turns that JSON into the .ipynb file. The notebook below is real output from build_notebook() for the JSON shown (shortened to two content cells).

  1. 1

    Upload

    api/routes/convert.py

    Input

    • attention.pdf posted to /convert/stream (multipart, 15 MB max)

    Output

    • PDF bytes, checked to start with %PDF-
    • page count for Metrics (pypdf, count only, no text read)
  2. 2

    LLM

    providers/ → LLM API, via generate_json()

    Input

    • the PDF bytes, sent as a file (base64 / raw bytes)
    • system prompt: how to teach a paper as a notebook (prompt.py)
    • user prompt: "Create a Google Colab notebook that implements and explains the attached research paper."
    • the JSON schema the reply must match:
    {
  "title":        string,
  "pip_packages": [string],
  "requires_gpu": boolean,
  "cells": [
    { "cell_type": "markdown" | "code",
      "source":    string }
  ]
}

    Output: JSON matching the schema

    {
  "title": "Attention Is All You Need",
  "pip_packages": ["einops"],
  "requires_gpu": false,
  "cells": [
    {
      "cell_type": "markdown",
      "source": "## Scaled dot-product attention\n$$\\text{Attention}(Q,K,V)=\\text{softmax}\\left(\\frac{QK^T}{\\sqrt{d_k}}\\right)V$$"
    },
    {
      "cell_type": "code",
      "source": "import torch\n\ndef attention(q, k, v):\n    scores = q @ k.transpose(-2, -1) / k.size(-1) ** 0.5\n    return scores.softmax(-1) @ v"
    }
  ]
}

    Plus token usage for the cost estimate. Everything a reader sees in the notebook comes from here.

  3. 3

    Builder

    notebook_builder/builder.py, build_notebook() with nbformat

    Input

    • the JSON from stage 2
    • the file name, from the upload: attention.ipynb

    What it does

    • checks the JSON: a title, at least one cell, valid types
    • title → first cell, with a "review the code" note
    • pip_packages → a !pip install cell, unsafe entries dropped
    • cells → copied in order, text unchanged
    • requires_gpu → Colab GPU setting (false here, so none)

  4. 4

    Save and reply

    convert.py + download.py

    Input

    • the notebook from stage 3, plus token usage and timings

    Output

    • ~/Downloads/attention.ipynb (an existing file is never overwritten)
    • an SSE result event for the dashboard: the notebook, its download link, cells and lines of code, packages, GPU flag, tokens, cost, timing, page count and session totals

A real run: non-linear activation functions

The same pipeline on a complete one-page paper with nine typeset equations. Open the PDF next to the notebook to see how each formula on the page became LaTeX in a markdown cell.

Input · PDF non-linear activation functions.pdf 1 page · 9 equations · 364 KB → Output · notebook non-linear activation functions.ipynb 30 cells (15 markdown, 15 code) · runs on CPU in about 40 s

How the formulas came out

In the PDFLaTeX in the notebook
Eq. 1, two layers collapse into one\underbrace{W_2W_1}_{W}\,x + \underbrace{W_2b_1+b_2}_{b}
Eq. 2, sigmoid\sigma(x)=\frac{1}{1+e^{-x}}
Eq. 6, GELU\frac{x}{2}\left[1+\tanh\left(\sqrt{2/\pi}\,(x+0.044715x^3)\right)\right]
Eq. 8, gradient bound\prod_{l=2}^L\|W_l\| \cdot\left(\tfrac14\right)^{L-1}
Eqs. 2–5, with derivativesgathered into one markdown table of $f(x)$ and $f'(x)$

What the code found when run

ActivationTest acc.First-layer gradient
sigmoid0.8552.9e-02, the smallest
tanh0.9603.3e-01
ReLU · Leaky ReLU · GELU0.960–0.9651.4e-01 – 2.3e-01
identity (baseline it added)0.8555.7e-01

Matches the paper's expected results: sigmoid trains slowest, the ReLU family fastest. The notebook also checks its own maths: every derivative matches finite differences, and backprop passes a gradient check. One claim in its dead-ReLU cell is not borne out by its own output, which is why each notebook says to review the code.

Where a setting comes from

The provider's model, base URL and tuning are taken from the first source that has a value:

PROVIDER itself and API keys come only from the environment; keys are never read from a file and never shown on the dashboard.
