1. No framework

The dashboard is plain HTML, CSS and JavaScript: no React, Vue or Tailwind, no npm, and no build step. FastAPI serves the files in api/static/ as they are.

LayerWhat is used
MarkupPlain HTML, one file per panel, put together by the server
StylesPlain CSS with custom properties (design tokens) in base.css
ScriptsNative ES modules (<script type="module">, import/export)
Server datafetch() for JSON; server-sent events from POST /convert/stream
LayoutCSS grid, responsive with two media queries

Why: the UI is small (two tabbed panels with six tabs, a drawer, and one conversion flow), so a framework would add more weight than it saves. Without one, the Python setup is the only setup: nothing to install or build, fast page loads, and no JavaScript dependencies to keep patched.

3. How the page is assembled

  1. The browser requests GET /.
  2. api/routes/dashboard.py reads index.html and replaces each <!-- include: panels/<name>/<name>.html --> line with that file's contents. Included files may include others, up to three levels: the Paper and Activity panels include their tabs (e.g. upload.html, output.html). Includes must stay inside api/static/.
  3. The page links base.css, then each panel's CSS, and loads app.js as a module, which imports the panels' scripts.
  4. Static files are served from /static with Cache-Control: no-cache (RevalidatedStaticFiles in api/main.py). The browser re-checks each file, so it never shows new HTML with old CSS or JS after an update; unchanged files come back as a cheap 304.

4. How a panel is written

Each panel's script exports one function that sets up its part of the page and returns the methods other code may call:

// panels/example/example.js
import { $, el } from "../../shared.js";

export function initExample() {
  // Find elements, attach listeners, load initial data.
  return {
    start(paper) { /* a conversion started */ },
    progress(update) { /* a progress event arrived */ },
    done(result) { /* the result event arrived */ },
    fail(message) { /* the conversion failed */ },
  };
}

Rules that keep the panels independent:

  • A panel changes only its own elements (ids it owns, e.g. m-* for Metrics, check-* for Run check).
  • Panels never import each other. Only app.js knows about more than one panel and passes data between them.
  • DOM is built with el(tag, props, ...children) from shared.js, and text is set with textContent, never innerHTML with server data, so model output cannot inject markup.

shared.js provides $() (get by id), el() (create an element), fmtInt, fmtBytes, fmtDuration, clock, scroll helpers (atBottom, follow) and readEvents(), which reads a server-sent event stream from a fetch() response.

Each server-sent event is handed by app.js to the panels that need it:

The notebook (as a string), its metrics, the depth and the verification report. The Download panel turns the notebook into a blob link.

error
output.failmetrics.failcheck.failupload status

status and detail. When a conversion starts, app.js also selects the LLM output tab, and when the result arrives it selects the Download tab. The full event format is documented on convert_pdf_to_notebook_stream in api/routes/convert.py.

Panels that do not depend on a conversion load their own data. Configuration calls GET /api/config and passes it to app.js, which gives the upload limit and run check availability to the Upload panel. Download calls GET /api/notebooks, Metrics calls GET /api/metrics/session, and the MCP log polls GET /api/mcp/events every 3 s, or every 0.7 s while a conversion runs; it reports new events to the Activity panel, which badges the MCP log tab while it is hidden. A configuration problem puts a "!" on the Configuration tab.

6. The Run check drawer

Run check is the only part of the UI that is not in the grid.

  • It is a section.panel.drawer, fixed over the right edge of the page, with the same panel frame and its own section colour. It has no backdrop, so the panels on the left stay usable.
  • It is used only when "Check that the notebook runs" is ticked. It slides in when the check starts; Collapse (or Escape) folds it into a vertical tab on the right edge, whose dot shows the status. On phones it opens full width.
  • It is drawn from the check events in progress updates: setup, plan (one per run, listing the cells), cell (running, ok with time and output, failed with the error) and repair (running, fixed, failed). See verify_notebook in notebook_builder/verify.py.

7. Layout and styling

  • Grid (in base.css): two panels side by side, Paper (1/3) and Activity (2/3). On a desktop window at least 1001 px wide and 640 px tall, they fill the window below the header and each tab scrolls inside, so the page never scrolls. Below 1000 px they stack, Paper first.
  • Tabs come from initTabs() in shared.js (ARIA tabs pattern: arrow keys, Home, End). Header actions marked data-tab-for="<tab id>" show only with their tab. Collapsible parts: Metrics' "More details" is a <details> whose open state, like the notebook depth, is remembered in localStorage (wrapped in try, so the page works without it).
  • Design tokens are CSS custom properties on :root: the palette, the status colours (--ok, --warn, --error), a sequence scale for ordered stages (--seq-1…--seq-5), a section tint and border per panel (--tint-<panel>, --line-<panel>), spacing, radius and fonts. Panel CSS uses only these tokens; a panel's section colour is set only in base.css.
  • The visual rules (white page, soft section tints, uppercase titles at the top-left, actions at the top-right, status colours only for status) are in the UI design guidelines.

8. Adding a tab

New views are usually new tabs of the Paper or Activity panel.

  1. Create api/static/panels/<name>/ with <name>.html (a div.tab-panel with id="<name>-panel", role="tabpanel", aria-labelledby="tab-<name>" and hidden), <name>.css and <name>.js (exporting init<Name>()).
  2. In paper.html or activity.html, add a tab button (role="tab", id="tab-<name>", aria-controls="<name>-panel", aria-selected="false", tabindex="-1") and an <!-- include: panels/<name>/<name>.html --> line. Header actions for the tab get data-tab-for="tab-<name>" hidden.
  3. In index.html, add the <link> for its CSS.
  4. In app.js, import and call init<Name>(), and pass it the events it needs.
  5. Add it to the page tests in tests/test_notebook.py (test_tabbed_panels, test_panel_assets_are_served).

A whole new panel also needs a grid area in base.css (and in the stacked layout) and a section colour (--tint-<name> / --line-<name>).

9. Testing

  • ./check.sh (or pytest) checks that the page assembles, that every panel is included, and that the panel assets are served. The backend events the panels read are tested in tests/test_progress.py and tests/test_verify.py.
  • There are no JavaScript unit tests. Check UI changes in a browser at desktop, tablet and phone widths, as the UI design guidelines require; node --check <file>.js catches syntax errors.

10. When to add a library

Updating the page by hand works because each panel owns a small part of it. If the UI grows a lot (many more panels, shared state between them, or complex forms), the first step should be a small library that also needs no build step, such as Alpine.js or Preact with htm, loaded as ES modules. A full React or Vue setup with a bundler would add an npm toolchain that this project does not otherwise need.
